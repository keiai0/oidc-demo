# セキュリティ攻撃デモ 実装計画

## Context

Phase 1〜3 で Authorization Code Flow（PKCE付き）が動作する状態。state / nonce / PKCE は OP・RP 両方で実装済み。

本計画では、これら3つのセキュリティ機構が**何から守っているか**を、実際に攻撃を体験することで学べるデモ機能を追加する。

---

## 目的

OIDC/OAuth の認可フローには複数のセキュリティ機構が組み込まれているが、初学者にとって以下の違いは分かりにくい:

- **state**: 何を防いでいるのか？
- **nonce**: state と何が違うのか？
- **PKCE**: これがないと何が起きるのか？

各機構を個別に無効化し、対応する攻撃が成功する様子を見せることで、それぞれの**存在意義**を体感させる。

---

## 前提知識: 3つの機構の整理

| 機構 | 守る対象 | 攻撃名 | 攻撃のタイミング |
|------|----------|--------|------------------|
| **state** | 認可レスポンス（callback） | CSRF（認可コードインジェクション） | 攻撃者が自分の認可コードを被害者に踏ませる |
| **nonce** | ID Token | ID Token リプレイ | 漏洩した ID Token を別セッションで再利用 |
| **PKCE** | 認可コード → トークン交換 | 認可コード横取り | 傍受した認可コードでトークンを取得 |

重要な違い:
- **state** はフロントチャネル（リダイレクト）の保護。RP 側で検証する
- **nonce** はトークンの保護。ID Token 内のクレームとして RP 側で検証する
- **PKCE** はバックチャネル（トークンエンドポイント）の保護。OP 側で検証する

---

## デモ設計

### 設計方針

1. **RP にセキュリティ設定パネルを設ける** — state / nonce / PKCE を個別に ON/OFF できるトグル
2. **OP にもデモモード用の検証スキップエンドポイント（またはフラグ）を設ける** — PKCE 検証の無効化
3. **攻撃シナリオをステップバイステップで UI 上にガイド表示する**
4. **各デモは独立して実行可能** — 1つずつ無効化して影響を確認できる

### 安全性の担保

- デモモードは環境変数 `DEMO_MODE=true` でのみ有効化される
- 本番環境では一切の検証スキップが発生しない
- デモモードが無効な場合、設定パネル自体が表示されない

## デモ 1: state 無効化 — CSRF 攻撃

> **RFC 参照:** RFC 6749 Section 10.12 (Cross-Site Request Forgery)
>
> 攻撃者が自分の認可コードやアクセストークンを被害者のクライアントセッションに注入し、
> 被害者の操作（銀行口座情報の保存など）が攻撃者のリソースに対して行われてしまう攻撃。
> クライアントは redirection URI の CSRF 保護を実装しなければならない（MUST）。
> その手段として state パラメータの利用が推奨される（SHOULD）。
>
> 関連: Section 4.1.1（state パラメータ定義）、Section 4.1.2（認可サーバーは state をそのまま返却）

### 攻撃シナリオ

**攻撃（セッション差し替え）:**
1. 攻撃者が OP で自分のアカウントでログインし、認可コード付き callback URL を取得する
2. 攻撃者はこの URL を被害者に踏ませる（メール、掲示板等で共有）
3. 被害者のブラウザが callback URL にアクセスし、攻撃者のアカウントで RP にログインしてしまう
   → **ここで攻撃成功** — 被害者のセッションが攻撃者のアカウントにすり替わっている

**被害（情報漏洩）:**
4. 被害者は自分のアカウントだと思い込んで通常通り操作する
5. 入力した個人情報・機密データは全て攻撃者のアカウントに保存される
6. 攻撃者は自分のアカウントにログインするだけで、被害者が入力した情報を全て閲覧できる
   → **ここで被害発生** — 被害者の情報が攻撃者の手に渡る

### デモフロー

**ステップバイステップ形式** — 各段階で「今何が起きているか」を見せつつ、操作はボタンでガイドする。

```
通常フロー:
  RP → 認可リクエスト (state=abc123) → OP → callback?code=xxx&state=abc123 → RP が state 検証 ✓

攻撃フロー (state 無効 — ステップ可視化):

  ── 準備 ──
  Step 1: 被害者（学習者）が通常のアカウントで RP にログイン済み
          → デモパネルに現在のログインユーザーが表示される
  Step 2: デモパネルで state を OFF にする
          → 「state を無効にしました。RP は callback 時に state を検証しません」と表示

  ── 攻撃 ──
  Step 3: 「攻撃者の認可コードを取得する」ボタンを押す
          → RP サーバーが攻撃者アカウントで OP に認証
          → 取得した callback URL を画面に表示（URL の中身が見える）
          → 「攻撃者はこの URL をメールや掲示板で被害者に送りつけます」と解説
  Step 4: 「被害者としてこのリンクを踏む」ボタンを押す
          → 表示されている callback URL に実際にアクセスする
          → state 検証なし → 攻撃者アカウントでログインしてしまう
          ⚠ 攻撃成功: 被害者のセッションが攻撃者のアカウントに差し替わった

  ── 被害の体験 ──
  Step 5: ログイン後のダッシュボードが表示される
          → 見た目はいつも通りのダッシュボード（被害者は異変に気づかない）
          → ここで「メモを保存」「プロフィールを編集」などの操作を行うと…
  Step 6: 操作結果の確認
          → 保存したメモ・編集したプロフィールは全て attacker のアカウントに紐づいている
          → 「あなたが入力した情報は、全て攻撃者のアカウントに保存されました」と表示
          → 攻撃前（victim@example.com）と攻撃後（attacker@example.com）を並べて比較

  ── 防御 ──
  Step 7: state を ON に戻して同じ攻撃を試みる → state 不一致で拒否される
```

### 必要な変更

**RP 側:**
- ログイン時に state の生成・Cookie 保存をスキップするオプション
- callback で state の検証をスキップするオプション
- 認可リクエスト URL に state パラメータを含めないオプション

**OP 側:**
- 変更なし（OP は state を透過的にエコーするだけで、検証責任は RP にある）

### 攻撃シミュレーションの段階的実行

`POST /api/demo/csrf-link` の処理:
1. 攻撃者用のテストアカウント（seed データに含める）で OP に認証する
2. 認可コード付き callback URL を取得して返す
3. **フロントエンドは URL をそのまま画面に表示する**（自動で開かない）
4. 学習者が URL の中身（`code=xxx` パラメータ等）を確認できる
5. 「被害者としてこのリンクを踏む」ボタンで、学習者自身が意図的にアクセスする

### UI ガイド表示内容

ステップ進行式の UI。フェーズごとに区切り、「今どの段階か」を明示する:

**準備フェーズ:**
- **Step 1 — 現在の状態確認**: 現在のログインユーザー情報を表示（「あなたは victim@example.com としてログインしています」）
- **Step 2 — state 無効化**: トグル操作後に「これで RP は callback の state を検証しなくなりました」と表示

**攻撃フェーズ:**
- **Step 3 — 攻撃者の準備**: 「攻撃者の認可コードを取得」ボタン → 取得した callback URL を表示し、「攻撃者はこの URL を被害者に送りつけます。URL に含まれる `code=xxx` が攻撃者の認可コードです」と解説
- **Step 4 — 攻撃の実行**: 「被害者としてこのリンクを踏む」ボタン → callback が実行される → **⚠ 攻撃成功: セッションが攻撃者のアカウントに差し替わりました**

**被害体験フェーズ:**
- **Step 5 — 偽のダッシュボード**: 見た目は通常と同じダッシュボードが表示される。被害者は異変に気づけない。ここで「メモを保存する」等のダミー操作を促す
- **Step 6 — 被害の可視化**: 操作した結果が全て attacker のアカウントに紐づいていることを表示。攻撃前（victim）と攻撃後（attacker）のアカウント情報を並べて比較。「あなたが入力した情報は、全て攻撃者のアカウントに保存されました」

**防御フェーズ:**
- **Step 7 — 防御の確認**: state を ON に戻して同じ攻撃を試み → state 不一致で拒否されることを確認

## デモ 2: nonce 無効化 — ID Token リプレイ攻撃

> **RFC 参照:** OpenID Connect Core 1.0 Section 2, Section 3.1.2.1, Section 3.1.3.7 Step 11, Section 15.5.2
>
> nonce はクライアントセッションと ID Token を紐付け、リプレイ攻撃を軽減する値（Section 2, 3.1.2.1）。
> 認証リクエストで nonce を送った場合、ID Token に nonce クレームが存在し値が一致することを
> 検証しなければならない（MUST — Section 3.1.3.7 Step 11）。
> クライアントはリプレイ攻撃を検出すべき（SHOULD）。検出方法はクライアントに委ねられる。
>
> 実装例（Section 15.5.2）: セッション Cookie にランダム値を保存し、そのハッシュを nonce として使用。
> ID Token の nonce とセッション Cookie のハッシュを比較して **"ID Token replay by third parties"** を検出する。
>
> Authorization Code Flow では nonce は OPTIONAL（Implicit / Hybrid Flow では REQUIRED）。
>
> 補足: RFC 9700 Section 4.5.3.2 では、nonce が Authorization Code Injection に対しても
> 有効であることが後から明文化された（OIDC Core 原文には Code Injection への言及はない）。

### ID Token リプレイ攻撃とは

nonce の防御メカニズムは **「セッションと ID Token の 1:1 紐付け」** である。
OIDC Core は攻撃の方向を限定せず "replay by third parties" とだけ述べているが、
具体的には以下の 2 パターンが考えられる:

**パターン 1 — なりすまし（盗んだトークンで被害者になりすます）:**
```
被害者が正規フローでログイン → ID Token が発行される
                ↓ 漏洩（ログ、キャッシュ、通信傍受等）
攻撃者が被害者の ID Token を入手
                ↓
攻撃者が被害者の ID Token を RP に送信し、被害者として認証を試みる
→ 攻撃者のセッション nonce ≠ 被害者の ID Token 内 nonce → 検出
```

**パターン 2 — 注入（自分のトークンを被害者に使わせる）:**
```
攻撃者が自分の ID Token を入手
                ↓
被害者のフロー途中で、攻撃者の ID Token を差し込む
→ 被害者のセッション nonce ≠ 攻撃者の ID Token 内 nonce → 検出
```

パターン 2 は state の CSRF（認可コード注入）と攻撃の方向が同じだが、
**検出するレイヤーが異なる**: state は認可レスポンス（リダイレクト）レベル、
nonce は ID Token（JWT クレーム）レベルで検出する。

nonce はどちらのパターンも防ぐが、Implicit Flow で REQUIRED になる理由
（ID Token がフロントチャネルに露出する = パターン 1 のリスクが高い）を考慮すると、
**パターン 1 がより直接的な脅威** といえる。

### デモで再現するシナリオ — パターン 1（なりすまし）

state デモがパターン 2（注入）をカバーしているため、nonce デモでは
**パターン 1（盗んだ ID Token でなりすまし）** を再現する。
これにより state と nonce の守備範囲の違いが体感できる。

**漏洩シナリオ:**
RP が ID Token をデバッグログに出力しており、攻撃者がログファイルにアクセスできた状況を想定する。

### 攻撃シナリオ

**攻撃（ID Token の再利用 → なりすまし）:**
1. 被害者が正規フローでログインし、RP が ID Token を取得する
2. RP のログに ID Token が記録される（デモではダッシュボードに表示して可視化）
3. 攻撃者がログから被害者の ID Token を入手する
4. 攻撃者が入手した ID Token を RP に送り、被害者として認証を試みる
   → **ここで攻撃成功** — nonce 検証がなければ、RP は ID Token を受け入れてしまう

**被害（なりすまし）:**
5. 攻撃者は被害者のアカウントとして RP にログインした状態になる
6. 被害者の個人情報・操作履歴にアクセスできる
   → **ここで被害発生** — 被害者のアカウントが攻撃者に乗っ取られる

### Authorization Code Flow における nonce の位置づけ

Authorization Code Flow ではトークン交換がバックチャネル（サーバー間通信）で行われるため、ID Token がフロントチャネルに露出しにくく、リプレイ攻撃のリスクは Implicit Flow より低い（nonce が OPTIONAL な理由）。しかし以下のケースでは依然として有効:

- RP のログに ID Token が記録されている場合（**デモではこのケースを再現**）
- ID Token をクライアント側にキャッシュ・保存している場合
- バックチャネル通信の TLS 終端が侵害された場合

### デモフロー

Authorization Code Flow では ID Token がフロントチャネルに直接露出しないため、**ログ漏洩シナリオをシミュレーション**する形式で実装する:

```
通常フロー:
  RP → トークン交換 → ID Token (nonce=xyz789) → RP が nonce 検証 ✓

攻撃フロー (nonce 無効 — ステップ可視化):

  ── 準備 ──
  Step 1: 被害者（学習者）が通常のアカウントで RP にログイン済み
          → ダッシュボードに ID Token の内容が表示される（ログ漏洩の可視化）
          → ID Token 内の nonce クレームの値をハイライト表示
  Step 2: デモパネルで nonce を OFF にする
          → 「nonce を無効にしました。RP は ID Token の nonce を検証しません」と表示

  ── 攻撃 ──
  Step 3: 「攻撃者がこの ID Token を入手した」と想定
          → 表示されている ID Token をデモパネルが自動コピー
          → 「攻撃者は RP のログからこの ID Token を入手しました」と解説
  Step 4: 「攻撃者としてこの ID Token でログインする」ボタンを押す
          → ID Token を /api/demo/replay-idtoken に送信（別セッションとして）
          → nonce 検証なし → RP が ID Token を受け入れる
          ⚠ 攻撃成功: 攻撃者が被害者の ID Token で認証された

  ── 被害の体験 ──
  Step 5: 攻撃者のセッションで被害者のダッシュボードが表示される
          → 被害者のプロフィール情報・操作履歴が閲覧できる状態
          → 「攻撃者は被害者のアカウントとして RP にログインしています」と表示

  ── 防御 ──
  Step 6: nonce を ON に戻して同じ攻撃を試みる
          → 「nonce が現在のセッションと一致しません」で拒否される
          → nonce がセッションと ID Token を紐付けている仕組みを解説
```

### 必要な変更

**RP 側:**
- ログイン時に nonce の生成・Cookie 保存をスキップするオプション
- callback でのトークン交換時に nonce の検証をスキップするオプション（openid-client の `expectedNonce` を省略）
- リプレイ攻撃シミュレーション用エンドポイント（`POST /api/demo/replay-idtoken`）
  - 任意の ID Token を受け取り、別セッションの文脈で検証する
  - nonce 検証あり: 送信元セッションの nonce と ID Token 内の nonce が不一致 → 拒否
  - nonce 検証なし: 署名のみ検証 → 受け入れ → 被害者のユーザー情報を返す

**OP 側:**
- 変更なし（OP は nonce を ID Token に含めるだけで、検証責任は RP にある）

### UI ガイド表示内容

ステップ進行式の UI。フェーズごとに区切り、「今どの段階か」を明示する:

**準備フェーズ:**
- **Step 1 — ID Token の確認**: ダッシュボードに ID Token のペイロードを表示。nonce クレームをハイライトし、「この値があなたのセッションと ID Token を紐付けています」と解説
- **Step 2 — nonce 無効化**: トグル操作後に「これで RP は ID Token の nonce を検証しなくなりました」と表示

**攻撃フェーズ:**
- **Step 3 — ID Token の漏洩**: 「攻撃者は RP のログからこの ID Token を入手しました」と解説。ID Token のペイロード（sub, email, nonce 等）を攻撃者視点で表示
- **Step 4 — リプレイ攻撃の実行**: 「攻撃者としてこの ID Token でログインする」ボタン → リプレイエンドポイントに送信 → **⚠ 攻撃成功: 被害者の ID Token が別セッションで受け入れられました**

**被害体験フェーズ:**
- **Step 5 — なりすましの確認**: 攻撃者が被害者のアカウント情報（名前、メール等）にアクセスできている状態を表示。「攻撃者は被害者になりすまして RP を利用できます」

**防御フェーズ:**
- **Step 6 — 防御の確認**: nonce を ON に戻して同じ攻撃を試み → 「nonce 不一致: この ID Token は現在のセッションで発行されたものではありません」で拒否。「nonce はセッションと ID Token を 1:1 で紐付けるため、別セッションでの再利用を防ぎます」と解説

## デモ 3: PKCE 無効化 — 認可コード横取り攻撃

> **RFC 参照:** RFC 7636 全文（特に Section 1, 1.1）、RFC 9700 Section 2.1.1, Section 4.5, Section 4.8
>
> PKCE は**認可リクエストの発行者 = トークンリクエストの発行者**であることを暗号的に証明する仕組み。
> クライアントが code_verifier を生成し、そのハッシュ（code_challenge）を認可リクエストに含め、
> トークンリクエスト時に code_verifier を提示する。OP は code_challenge と照合して検証する。
>
> RFC 7636 の主な想定: ネイティブアプリでの認可コード傍受
> （TLS 外の通信経路 — OS 内プロセス間通信、カスタム URI スキームの横取り等）。
>
> RFC 9700 で防御対象が拡張: Authorization Code Injection にも有効（Section 4.5）。
> また、全てのクライアント（public / confidential 問わず）で PKCE を MUST としている（Section 2.1.1）。
> RFC 7636 時点では public client が主なターゲットだったが、RFC 9700 で全クライアントに拡大された。

### PKCE が防ぐ攻撃

PKCE の防御メカニズムは **「認可リクエスト ↔ トークンリクエストの暗号的紐付け」** である。
これにより以下の攻撃を防ぐ:

**認可コード傍受（RFC 7636 の主な想定）:**
```
正規クライアントが認可リクエストを送信 → OP が認可コードを発行
                ↓ 傍受（カスタム URI スキーム横取り、ブラウザ拡張、ログ等）
攻撃者が認可コードを入手
                ↓
攻撃者がトークンエンドポイントに認可コードを送信
→ PKCE あり: code_verifier を知らないため失敗
→ PKCE なし: トークン取得成功 — 攻撃者が被害者のリソースにアクセス
```

**認可コード注入（RFC 9700 で追加）:**
```
被害者のフロー途中で、攻撃者が別途取得した認可コードに差し替え
→ PKCE あり: 被害者の code_verifier と攻撃者のコードの code_challenge が不一致で失敗
→ PKCE なし: 攻撃者のアカウントでトークンが発行される
```

注入攻撃は state / nonce でも検出可能だが、PKCE は **OP 側で検証** するため、
RP 側の実装ミス（state 検証漏れ等）に依存しない強固な防御レイヤーとなる。

### 3つの機構の守備範囲の違い

| 機構 | 紐付ける対象 | 検証する側 |
|------|-------------|-----------|
| **state** | 認可リクエスト ↔ コールバック（リダイレクト） | RP |
| **nonce** | セッション ↔ ID Token（JWT クレーム） | RP |
| **PKCE** | 認可リクエスト ↔ トークンリクエスト（暗号的） | **OP** |

PKCE だけが OP 側で検証される点が重要。state と nonce は RP 側の検証に依存するため、
RP の実装に不備があれば突破される。PKCE は OP が検証するため、RP の実装品質に依存しない。

### デモで再現するシナリオ — 認可コード傍受

本デモでは RFC 7636 の主な想定である**認可コード傍受**を再現する。
RP のフローで発行された認可コードを攻撃者が入手し、
code_verifier なしでトークンエンドポイントに直接リクエストを送るシナリオ。

### 攻撃シナリオ

**攻撃（認可コードの横取り → トークン取得）:**
1. 被害者が RP でログインフローを開始し、OP で認証する
2. OP が認可コード付き callback URL をリダイレクトで返す
3. 攻撃者がこの認可コードを傍受する（デモではフロー中のコードを画面に表示して可視化）
4. 攻撃者が認可コードを使って、code_verifier なしでトークンエンドポイントにリクエストする
   → **ここで攻撃成功** — PKCE がなければ、OP はトークンを発行してしまう

**被害（リソースアクセス）:**
5. 攻撃者はアクセストークンを取得する
6. アクセストークンを使って被害者のリソース（UserInfo 等）にアクセスできる
   → **ここで被害発生** — 被害者の個人情報が攻撃者に渡る

### デモフロー

```
通常フロー:
  RP → 認可リクエスト (code_challenge=hash(verifier)) → OP
  OP → callback?code=xxx → RP
  RP → トークンリクエスト (code=xxx, code_verifier=verifier) → OP が検証 ✓

攻撃フロー (PKCE 無効 — ステップ可視化):

  ── 準備 ──
  Step 1: 被害者（学習者）が RP でログインフローを開始する
          → デモパネルで PKCE を OFF にしてからログイン
          → 「PKCE を無効にしました。認可リクエストに code_challenge は含まれません」と表示
  Step 2: OP で認証し、callback にリダイレクトされる
          → フロー中に発行された認可コードをデモパネルに表示
          → 「この認可コードが callback URL に含まれています: code=xxx」と解説

  ── 攻撃 ──
  Step 3: 「攻撃者がこの認可コードを傍受した」と想定
          → 認可コードをデモパネルが自動コピー
          → 「攻撃者はブラウザ拡張やログ等からこの認可コードを入手しました」と解説
  Step 4: 「攻撃者としてこのコードでトークンを取得する」ボタンを押す
          → code_verifier なしでトークンエンドポイントにリクエスト
          → PKCE 無効 → OP がトークンを発行してしまう
          ⚠ 攻撃成功: 攻撃者が code_verifier なしでトークンを取得できた

  ── 被害の体験 ──
  Step 5: 取得したトークンで被害者の情報を表示
          → アクセストークンで UserInfo エンドポイントにリクエスト
          → 被害者の名前・メール等が攻撃者に見える状態
          → 「攻撃者は被害者のアクセストークンで個人情報を取得しました」と表示

  ── 防御 ──
  Step 6: PKCE を ON に戻して同じ攻撃を試みる
          → code_verifier なし → OP が `invalid_grant` で拒否
          → 「認可リクエスト時の code_challenge と一致する code_verifier がないため、
              OP がトークン発行を拒否しました」と解説
```

### 必要な変更

**RP 側:**
- ログイン時に code_verifier / code_challenge の生成をスキップするオプション
- 認可リクエスト URL に code_challenge / code_challenge_method を含めないオプション
- callback でのトークン交換時に code_verifier を送信しないオプション
- callback 時にフロー中の認可コードをデモパネル表示用に保持する仕組み

**OP 側:**
- デモモード時、PKCE 検証をスキップするオプション（client の `require_pkce` を一時的に無効化）
- PKCE パラメータなしでも認可コードを発行するオプション

**攻撃シミュレーション用エンドポイント:**
- `POST /api/demo/steal-code` — 認可コードを受け取り、code_verifier なしでトークンエンドポイントにリクエスト
  - 成功時: 取得したアクセストークンで UserInfo を取得し、被害者の情報を返す
  - 失敗時: OP のエラーレスポンス（`invalid_grant`）をそのまま返す

### UI ガイド表示内容

ステップ進行式の UI。フェーズごとに区切り、「今どの段階か」を明示する:

**準備フェーズ:**
- **Step 1 — PKCE 無効化 + ログイン**: PKCE を OFF にした状態でログインフローを開始。「認可リクエストに code_challenge が含まれていません」と表示
- **Step 2 — 認可コードの確認**: フロー中に発行された認可コードを表示。「この値が認可コードです。通常は RP だけが使いますが、傍受されると…」と解説

**攻撃フェーズ:**
- **Step 3 — 認可コードの傍受**: 「攻撃者はブラウザ拡張やログ等からこの認可コードを入手しました」と解説。認可コードを攻撃者視点で表示
- **Step 4 — トークン取得の試行**: 「攻撃者としてこのコードでトークンを取得する」ボタン → code_verifier なしでトークンリクエスト → **⚠ 攻撃成功: トークンが発行されました**

**被害体験フェーズ:**
- **Step 5 — 個人情報の窃取**: 取得したアクセストークンで UserInfo を取得し、被害者の情報（名前、メール等）を表示。「攻撃者はこのトークンで被害者の個人情報にアクセスできます」

**防御フェーズ:**
- **Step 6 — 防御の確認**: PKCE を ON に戻して同じ攻撃を試み → `invalid_grant` で拒否。「OP は code_verifier と code_challenge の一致を検証するため、認可コードだけではトークンを取得できません」と解説
