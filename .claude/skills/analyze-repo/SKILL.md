# 使用方法
#
# /analyze-repo <REPO_URL> <CONTEXT>
#
# 引数:
#   REPO_URL (必須): 調査対象のGitHubリポジトリURL
#                     例: https://github.com/dexidp/dex
#   CONTEXT  (必須): 調査の目的・背景を説明するテキスト
#                     なぜこのリポジトリを調査するのか、何を学びたいのかを記述する
#
# 自動推定:
#   PROJECT_NAME: REPO_URL の最後のパスセグメントから自動推定（.git は除去）
#                 例: https://github.com/dexidp/dex → dex
#
# 出力:
#   docs/research/<PROJECT_NAME>-analysis.md
#
# 例:
#   /analyze-repo https://github.com/dexidp/dex "GoでOAuth2/OIDC関連の機能を新規開発する予定。設計思想と実装パターンを学びたい"
#   /analyze-repo https://github.com/ory/hydra "Go製OAuth2 Authorization Serverの設計を参考にしたい"
#   /analyze-repo https://github.com/go-chi/chi "軽量Goルーターの設計パターンを調査したい"
#
# 注意:
#   - クローンしたリポジトリは調査完了後に自動削除されます

$ARGUMENTS のリポジトリをクローンして徹底的に調査し、
自分たちのプロジェクトで参考にすべき点・参考にすべきでない点を整理したドキュメントを
`docs/research/<PROJECT_NAME>-analysis.md` として保存してください。

- REPO_URL は `$ARGUMENTS` の最初のトークン（スペース区切り）
- PROJECT_NAME は REPO_URL の最後のパスセグメント（`.git` は除去）
- CONTEXT は `$ARGUMENTS` の REPO_URL 以降のテキスト全体

## 前提
- ただし盲目的に踏襲するのではなく、参考にすべきでない点やより良い選択肢も把握したい
- 自分たちのプロジェクトは新規開発なので、後方互換性の制約はない

## 調査手順

1. リポジトリを一時ディレクトリにクローンする
2. README.md, CONTRIBUTING.md, docs/ 等のドキュメントを最初に読み、プロジェクトの目的と思想を理解する
3. go.mod で依存ライブラリとGoバージョンを確認する
4. ルートのファイル構成と主要な設定ファイルを確認する
5. ディレクトリ構造を再帰的に探索する
6. 主要なインターフェース・構造体・エントリーポイントのコードを読む
7. テストコードを複数ファイル読み、テスト戦略を把握する
8. git log --oneline -30 でコミット履歴の傾向を確認する
9. Makefile, .golangci.yml 等のツール設定を確認する
10. Issue/PRテンプレートがあれば確認する

## ドキュメント構成

### Part 1: プロジェクト概要
- プロジェクトの目的・スコープ・解決している課題
- ライブラリ/フレームワーク/アプリケーションのどれか
- 設計哲学（README・コード・ドキュメントから読み取れるもの）
- Goバージョン・主要な依存ライブラリ一覧（go.modから抽出）
- プロジェクトの成熟度（スター数、最終コミット日、コントリビューター数等）

### Part 2: アーキテクチャ分析

#### ディレクトリ構成
- ツリー図（主要ディレクトリのみ、深さ2程度）
- 各パッケージの責務とパッケージ間の依存方向

#### 設計パターン
- 採用しているデザインパターンを具体的なコード箇所と共に説明
- インターフェース設計の方針（サイズ、分割粒度、埋め込みの使い方）
- 構造体の設計（コンストラクタパターン、Functional Options等）
- 依存性注入の方法
- エラーハンドリングのパターン
- context.Context の活用方法

#### モジュール分割の思想
- ドメインの主要概念をどうパッケージに分離しているか
- 抽象化レイヤーの境界と設計意図
- コンポーネント間の合成・連携パターン

### Part 3: Go実装の詳細分析
- パッケージ構成がGo標準のプロジェクトレイアウトに沿っているか
- internal パッケージの活用有無と方針
- エクスポート/非エクスポートの判断基準
- 命名規則（パッケージ名、インターフェース名、レシーバ名、変数名）
- ファイル分割の粒度とファイル命名
- GoDocコメントの書き方・充実度
- goroutine / channel / sync の使い方（並行処理パターン）
- go generate の活用有無

### Part 4: テスト戦略
- テストフレームワーク・ライブラリ（標準testing, testify, gomock等）
- テストの種類と比率（unit / integration / e2e）
- テーブル駆動テストの採用状況
- モック・スタブの作り方
- テストヘルパー・フィクスチャの管理方法
- テストファイルの命名・配置規則
- テストカバレッジの状況

### Part 5: CI/CD・開発ツール
- CI構成（GitHub Actions等）
- Linter設定（golangci-lint の設定内容を詳細に）
- Makefile のタスク構成
- リリース方法・バージョニング戦略
- コミットメッセージ規約
- PR/Issueテンプレート

### Part 6: 参考にすべき点（Adopt）
具体的なコード例・ファイルパスを添えて説明：
- 優れた設計判断とその理由
- Goらしい（idiomatic）実装パターン
- テスタビリティを高めている工夫
- 拡張性・柔軟性を実現している仕組み
- ドキュメンテーションの良い習慣
- セキュリティ面で参考になる実装
- このドメイン特有の優れた設計判断
- 自分たちの新規プロジェクトにそのまま適用できるパターン

### Part 7: 参考にすべきでない点（Avoid）
なぜ参考にすべきでないかの理由と代替案と共に説明：
- 過度な抽象化や複雑化をしている箇所
- 歴史的経緯で残っているレガシーな設計（deprecatedなコード、古いGoパターン等）
- 現在のGoバージョンならもっと良い書き方ができる箇所（generics, errors.Is/As, slog等）
- テスト不足・テストが甘い箇所
- ドキュメントと実装の乖離がある箇所
- 密結合になっている箇所
- エラーハンドリングが不十分な箇所
- セキュリティ上の懸念がある実装パターン
- OSSライブラリ特有の妥協（後方互換性維持等）で、新規プロジェクトでは不要なもの
- 依存ライブラリの選定で、現在はより良い選択肢があるもの

### Part 8: 新規プロジェクトへの適用ガイド
- このプロジェクトの設計から取り入れるべきアーキテクチャ骨格の提案
- 推奨するパッケージ構成（調査対象の改善版として）
- 使っていないが新規なら導入すべき現代的Go技法
- 最初に定義すべきインターフェース群のリスト

### Part 9: 総合評価サマリー
- 表形式で各観点（設計/テスト/ドキュメント/セキュリティ/拡張性/Goらしさ）を5段階評価
- 最も学ぶべきトップ3の設計判断
- 最も注意すべきトップ3のアンチパターン
- フォークして使うべきか、参考にして自前実装すべきかの判断材料

## 出力ルール
- 事実と主観的評価を明確に区別する
- コード例を引用する場合は該当ファイルパスを必ず明記する
- 「参考にすべきでない」は批判ではなく「コンテキストが異なる」「より良い選択肢がある」という視点で書く
- 各セクションの冒頭に1-2行の要約を入れる
- Go公式のベストプラクティス（Effective Go, Go Code Review Comments等）との比較を適宜入れる
- 最後にクローンしたリポジトリは削除する
